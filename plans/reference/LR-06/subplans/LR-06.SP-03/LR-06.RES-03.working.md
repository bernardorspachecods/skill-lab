# Working

## Brief and scope

**Task:** compare conditions that make feedback/revision loops in AI-agent user workflows helpful, harmful, or unproven, emphasizing feedback reliability/relevance, initial output, iteration/stopping, independent verification, comparable resources, user control/effort, proxy alignment, and failure recovery. Intended plan consumer: a later reader-facing knowledge entry on useful feedback-loop cases, when/how they work, and what evidence supports them.

**Scope assumption:** retain the direct information-work workflow boundary set by LR-06. Human–AI decision experiments and model-only refinement studies count as bounded-adjacent mechanism/failure evidence, not direct workflow evidence. Do not claim exhaustive coverage. Reviewed S1/S2 are source and terminology entry points; their prior search routes and source sets are not a closed collection.

**Priority questions:**

1. Does feedback signal reliability/relevance or initial quality alter the direction of a later outcome?
2. When does human review, checkpointing, or revision improve an independently assessed result, and when does it add error/effort?
3. What stopping, verification, and failure-recovery evidence exists, and what remains untested in direct agent workflows?
4. Do reported efficiency, usefulness, and quality measures track user value independently of the loop's own metric?

## Finding cards (working synthesis)

**F1 — Reliable signal is a condition, not a synonym for iteration.** In Ahuja et al.'s bounded perceptual experiments, accurate feedback improved independent judgments and biased feedback amplified bias (E1); repeated exposure showed slopes in both directions. Cross-case inference: a workflow should assess the feedback source, not assume that another cycle is corrective. This was not tested as a user-agent protocol.

**F2 — Guardrailed, optional feedback can support a useful revision without proving final task correctness.** The ICLR review-feedback RCT reports modest uptake, suggestion incorporation and selected blind quality improvements, with a null mean score-change endpoint (E4). Conditions include targeted feedback categories, high threshold/automated reliability checks, an explicit retry cap, users retaining final control and opportunity to revise before deadline. The agent's own internal score is not the independent quality outcome.

**F3 — Self-critique has a failure channel.** In the Huang benchmark, without an oracle, a model's extra calls can reduce correctness, in part because the model changes correct answers to incorrect ones (E5). Fang et al. show a distinct over-correction channel when a model is prompted to justify and repair correct code (E6). Cross-case inference: revision should be validated against independent evidence, especially where a “fix” could introduce changes.

**F4 — Human control does not guarantee meaningful correction.** In PLOS, edit permission increased confidence and algorithm uptake while hurting prediction accuracy (E3). S2's checkpoint simulation likewise shows diagnosis benefit depends on error timing and cost. A useful interface needs a real signal/verification method, and an outcome measure that can show whether edits helped.

**F5 — Treat proxies and resource costs separately.** Review length/uptake, benchmark score, task time, user ratings and actual quality answer different questions. METR's 2026 note illustrates that agent wait can overlap with other tasks, task mix changes, and AI availability alters participation, so “time per task” may be a poor user-value proxy (E7). S2 evidence is retained as its own source context, not pooled.

## Validation / search stop assessment

- Coverage includes direct reviewed S1/S2 loops, one high-scale live user-facing feedback/revision RCT, controlled adjacent positive and negative signal-quality cases, human intervention with true outcome labels, model-only self-correction, code repair/verification benchmarking, and a contemporary productivity measurement update.
- Each material source was read at relevant methods/results/discussion locations; claim entries preserve exact sections/lines and limitations. VOR/preprint duplicates and within-paper experiments are grouped by provenance. Search-result snippets are not used as evidence.
- Located category coverage: positive (accurate-signal condition, review revision, and bounded test-grounded repair gains in narrower code scopes), mixed/null (noisy/biased contrasts, no significant mean reviewer-score shift, project-level nonconvergence and scope dependence in E8, late-check cost tradeoff from S2), adverse (biased-signal learning, inaccurate human corrections, unsupported self-correction, over-correction; measured task-time slowdown in METR's old-tool setting), countervailing/qualifying (reliable feedback and external verification help in bounded task cases). No direct agent-user adaptive stopping RCT with independent quality and total cost located.
- Main remaining uncertainty is direct transfer: how an agent user should choose the signal, verification mode, revision count, and stop point for research/planning/drafting/analysis/coding tasks under real resource budgets. No single study jointly manipulates all those conditions. High variability and context prevent a single numerical effect size.
- **Stop rationale:** The S3 coverage map includes primary source roles for direct user revision, human–AI interaction, model-only refinement, code verification and productivity measurement; meaningful version/citation routes were followed; an adverse/null refutation pass was run. Further results can expand examples, but the present evidence already identifies the decision-changing boundaries and precise direct-evidence gaps. Stop here for S3 review rather than infer an optimal loop policy. This is bounded collection adequacy, not exhaustive web recall.
